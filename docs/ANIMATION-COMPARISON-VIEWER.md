# CJ64 animation comparison viewer

The viewer compares the same locally selected GTA San Andreas `ped.ifp` clip on two GLB models generated by the CJ64 rig-transfer workflow:

- **GTA original:** the uploaded FBX with its original 58-bone skeleton.
- **SM64CoopDX retarget:** the same CJ geometry, using the exact 20-node target skeleton and the converted per-vertex weights used by the Fast64 actor export.

## Use

1. Open the CJ64 Animation Comparison page from the GitHub Actions summary (or open the `CJ64-Animation-Comparison-Viewer` artifact and its `index.html` bundle from a local static web server).
2. On the phone, select the original `ped.ifp` through **Elegir archivo .ifp**.
3. Choose an animation, starting with `IDLE_stance` or `WALK_player`.
4. Use play/pause, frame stepping, speed, and the timeline. Drag each model to rotate it; pinch to zoom.

The IFP is parsed in browser memory. It is not uploaded, saved to the repository, included in Pages, or sent to the model-export workflow.

## How the two sides are produced

The source view follows the repository's original Blender IFP importer: each source quaternion is applied as a local pose channel to its mapped FBX bone, preserving the source skeleton's own bind pose and helper-bone hierarchy. The GTA `Normal` root rotation is retained on this side. Type-4 local translations are interpolated and applied to mapped non-root bones, such as `Pelvis` in `FALL_fall`.

The target view uses the same 30 FPS retarget and channel conversion as `tools/generate_cj_sm64_animations.py`: source global deltas, target-parent compensation, XYZ Euler extraction, 16-bit angle channels, and interpolation between generated samples. The target mesh's original vertex-group assignments after the 20-node mapping are reused; the preview exporter only restores the original FBX PBR material/UV data so it can be displayed as GLB.

The ported SM64 view uses the exact 30 FPS channel generation path but deliberately suppresses the GTA `Normal` root rotation and all translations. That matches the current game integration: MarioState owns the player's world orientation and movement, and the SM64 animation tables only carry the 20 rotation channels. The viewer therefore makes any motion lost by this reduction visible instead of hiding it.

## Validation limits

This is a rig and animation comparison, not the DynOS renderer. It does not reproduce F3D/F3DEX2E microcode, TMEM texture slicing, game lighting, runtime animation scheduling, MarioState action changes, collision, or gameplay movement. A good-looking retargeted GLB must still be tested inside SM64CoopDX before the game mod is considered correct.

If GitHub Pages is not enabled for the repository, the workflow still uploads the complete viewer and paired GLBs as a downloadable artifact. To get a permanent web URL, set **Repository Settings → Pages → Build and deployment → Source: GitHub Actions**, then rerun the rig-transfer workflow.
